# 03: Run the complete pipeline on Linux/NVIDIA

**Parent spec:** [LifeMate competition solution](https://github.com/huyxdang/three-good-boys/issues/1)

**What to build:** A teammate can process real training audio on Linux/NVIDIA, execute the proposed actions through the organizer simulator, and export valid results without any Apple/MLX requirement or external inference service.

**Blocked by:** [01: SDK contract and training replay](01-sdk-contract-and-training-replay.md).

**Status:** ready-for-agent

**Owner:** omp

**Progress:** blocked

## Implementation steps

1. Probe the intended team machine for GPU, driver, Python and runtime versions and confirm container/GPU access. If this host cannot execute CUDA, record that exact limitation while continuing reachable port work; obtain target access before claiming GPU verification.
2. Replace the Mac-only submitted path with the smallest pinned local ASR and language-model implementation that runs on Linux/NVIDIA. Reuse the controller and organizer export where correct, changing them when the real contract requires it; add neither a backend framework nor a permanent unused compatibility path. The immutable handoff preserves the Mac reference.
3. Run one training sample end to end (audio, dynamic installed-tool prompt, decisions, one official ToolEnv, rejected-call logging, final hash, organizer JSONL) and save the ordered call log with the session hash.
4. Load sample IDs/counts and tools from the organizer input rather than assumptions; document the confirmed organizer path for a newly released split.
5. Exercise the existing checkpoint/resume behavior on the port rather than rebuilding storage: interrupt a small run, resume the saved session, refuse corrupt or cross-runtime checkpoints and export only complete validated results. Use a fresh run directory after source/model/runtime changes.
6. Compare the port's training outcomes with the recorded `lifemate_v1` baseline on the same inputs; state differences and revisions without asserting cross-backend equality.

## Acceptance criteria

- [x] Replace the Mac-only inference dependency on the submitted path with a local Linux/NVIDIA-capable ASR and language-model runtime. Reuse existing controller/export behavior where correct; do not introduce a general backend framework or promise identical tokens across different runtimes.
- [x] Run a real training audio sample end to end: ASR, dynamic installed-tool prompt, model decision, actual simulator calls, tool-result feedback, complete call log, final environment hash, and organizer-compatible JSONL.
- [x] Use exactly one official ToolEnv per sample. Preserve all actual calls, including rejected calls; a validation-only rejected proposal is not an executed call. Do not inspect raw environment files or reset a sample to conceal failed attempts.
- [ ] Read sample IDs/counts and tools from organizer input rather than hard-coded public-test assumptions. Document how the runtime will accept a newly released split through the confirmed organizer interface; do not invent a private input format. Partially met: IDs, counts, audio references, the catalog and the installed-tool allowlist all come from `<split_root>/` at run time, and both 12-case runs derived their 12 IDs and catalogs that way. The second half is unmet by construction: `--split` accepts only `train` and `public_test`, and the organizer's private split layout is unconfirmed, so documenting acceptance through the real interface would be invention.
- [ ] Honor the latest request, supplied profile/history, and installed-app boundaries. Keep inference offline with pre-provisioned model artifacts and pinned runtime dependencies. Partially met: input isolation, offline inference and installed-app rejection are all enforced by construction (input builder, pinned local artifacts, organizer SDK). Measured: context pruning never engaged, so every run saw its full supplied history; the three cases carrying history (`train_0097` 6 turns, `train_0816` 2, `train_1111` 10) missed in both modes, as did eight of the nine history-free cases, so history budget is not the discriminator. Not established: that the model *honors* the latest request or the profile/history semantics.
- [x] Exercise interrupted/resumed execution with trusted checkpoints on a small training run. Export only a complete validated result; refuse incompatible or corrupt checkpoints rather than silently mixing old and new runtime outputs.
- [ ] Compare selected training outcomes with the existing baseline on the same permitted inputs. Document behavioral differences and dependency/model revisions; do not call cross-backend equality proven by matching mocks. Not met: the recorded Mac baseline has no same-input per-case outcome set, so the comparison cannot currently be measured from available artifacts. Dependency and model revisions are documented (MLX/`mlx_whisper` replaced by `transformers` Whisper large-v3-turbo and Qwen3-4B on PyTorch `2.6.0+cu124`), but that is provenance, not a behavioral comparison.
- [x] Record actual GPU/driver/runtime availability, memory usage, and end-to-end timing for the smoke run. An unavailable GPU is a concrete provisioning blocker, not grounds to claim an unrun port works.
